# 安定性と互換性ポリシー

本章では、コンパイラのバージョンアップに際して利用者の既存コードや外部連携ツールが破損しないよう、Tsuzuri が**安定として保証する対象**と**保証しない対象**、後方互換性と進化を両立する**エディション制度（Edition 2026 / 2027 / 2028）**、宣言の非推奨化（`@deprecated`）の手順、および `tsuzuri api-diff` を用いた公開 API 差分検査の基準を定義します。

## 要点

- ソースコードの後方互換性の単位は **エディション（Edition）** です。同じエディションを指定したパッケージは、新しいコンパイラへ更新してもバグ修正を除き同じ意味でコンパイル・実行できます。
- 公開 C / WebAssembly ABI、診断コードと原因識別子 `kind`、CLI の `--json` スキーマ、知識グラフスキーマ（`tz-kg/1` / `tz-facts/1`）、MCP ツールスキーマ、および適合性規則 ID（`AREA-NNN`）は破壊的変更から保護されます。
- 一方、内部の LLVM IR 構造、ビルドキャッシュ形式、人間向けの診断メッセージ文言やヒント文言、新規警告の追加有無は改善のため変更されることがあります。
- 現在サポートされているエディションは `2026`・`2027`・`2028` の 3 つであり、新規プロジェクトやマニフェストなし入力の既定は最新の **Edition 2028**、既存マニフェストで `edition` を省略した場合の既定は **Edition 2026** です。異なるエディションの依存パッケージを 1 つのプログラム内でそのまま組み合わせてリンクできます。

## 安定性保証の範囲

### 安定として保証する項目

| 対象領域 | 保証される不変条件 |
| --- | --- |
| エディション別の構文と意味論 | 同一エディションにおける型付け、評価順序、所有権・借用規則、数値のオーバーフロー・丸め・NaN・トラップ条件（コンパイラのバグ修正を除く） |
| 標準ライブラリの公開 API | 公開済みモジュール・型・関数の削除や破壊的なシグネチャ変更を行わない（後述の「既知の例外」を除く） |
| 公開 C / WebAssembly ABI | `export def` の `tz_<name>` シンボル、`--emit header` の C 型レイアウトと多重インクルード保護、`tsuzuri_*` ランタイム境界シンボル、`extern` のリンク名・import 名、`.trap.json` および `.overflow.json` の既存 JSON キー |
| 診断コード・重要度・`kind`・JSON キー | 診断コード（`E1012` 等）や `kind`（`use_after_move` 等）の削除・改名・別条件への再利用を行わない（1 つの `kind` をより細かい `kind` へ分割する拡張のみ可）。`--json` の既存フィールド名・順序・`role`・`applicability` 語彙を維持する |
| 適合性規則 ID | `spec/rules/` の規則 ID（`OWN-012` 等）を再利用しない。意味が変わる場合は `retired` とし新番号を付与する（[仕様規則体系と適合性テスト](./conformance.md) 参照） |
| 知識グラフスキーマと `tsuzuri kg` | `target/tz/kg/` のファイル構成、`manifest.json`（`tz-kg/1`）および `nodes.jsonl`・`edges.jsonl`・`tests.jsonl`・`facts/`（`tz-facts/1`）・`layout/` の既存キー名と意味、終了コード規約（フィールドや列挙値の追加は互換拡張として行われる） |
| 各種 CLI / MCP 構造化出力 | `tsuzuri guide --json`（`tz-guide/1`）、`tsuzuri fix --json`、`tsuzuri explain --json`、`tsuzuri api-diff --json`、`tsuzuri audit --json`（`tz-audit/1` と 9 種の権限語彙）、`tsuzuri find --json`、`tsuzuri kg impact --json`、`tsuzuri kg diagram --json`、`tsuzuri test --doc --json`、および `tsuzuri mcp` のツール名・入力引数・`structuredContent` の既存キー |

### 保証の対象外となる項目

| 対象領域 | 保証外とする理由 |
| --- | --- |
| 生成される LLVM IR・内部シンボル・内部メモリ配置 | 最適化の改善やレコードフィールドの詰め替え最適化等のために変更される（`@c_layout` や公開 ABI 境界を除く） |
| ビルドキャッシュ・構文解析キャッシュの内部形式 | コンパイラバイナリが更新されれば自動的に無効化・再生成される |
| 人間向けメッセージ・ガイド・要約カードの文言 | 診断の `message`・`help`・修正案 `title`、`tsuzuri explain` や `tsuzuri guide` の英語本文、知識グラフ `brief` カードの行順序や表現、MCP の説明文、生成図表の細部レイアウト（Mermaid 構文としての妥当性は維持） |
| 新規警告の発行と `--deny-warnings` の合否 | 解析精度の向上や依存パッケージの `@deprecated` 追加により新たな警告が報告される場合がある（`tsuzuri test` の整数折り返し検出箇所の増減を含む） |
| 標準ライブラリ関数が内部で要する権限 | 内部実装の改善に伴い `[capabilities]` が導出する所要権限が変化する可能性がある（発生時はリリースノートで告知） |
| 実験的と明記された機能 | GPU カーネル出力（`wgsl` / `spirv` 系および `Gpu` モジュール）などは仕様確定まで変更される場合がある |

## エディション制度（Edition 2026 / 2027 / 2028）

エディションは、既存のパッケージを壊すことなく言語の構文や既定規約を整理・進化させるためのオプトイン機構です。すべてのエディションのパッケージは共通の単一標準ライブラリと中間表現へコンパイルされるため、Edition 2026 の依存ライブラリを Edition 2028 のアプリケーションから何の障壁もなく呼び出せます。

### 各エディションの仕様比較

| エディション | 状態と既定の適用先 | 主な言語規則の特徴 |
| --- | --- | --- |
| `2026` | `Tsuzuri.toml` で `edition` キーを省略したときの既定版（既存マニフェスト保護のため固定） | 初版仕様。通常の `def` の無印引数は所有権移動（値渡し）が既定。短い数値接尾辞（`86uy`）、記号借用（`&x` / `*r` / `&T`）、バックスラッシュなしラムダ（`x -> e`）を受理。裸の `a..b` スライスは半開区間 |
| `2027` | サポート版 | 通常の `def` における非 Copy 具体型・型変数・関数引数を**共有借用（読み取り）既定**とし、所有権移動は `own T`、排他更新は `mut T`（およびフィールド・要素パスへの排他借用 `ref mut r.field`）で記述。`Array` / `List` のコールバックや `Vec.push` も借用・排他更新入口が既定（旧契約は `_owned`）。重複表記 6 種を `E0004` で廃止 |
| `2028` | **現在の最新版（`Edition::LATEST`）**。`tsuzuri new`、マニフェストなし入力、`script`、`repl`、標準ライブラリの既定版 | Edition 2027 の引数・借用規約を継承しつつ、ブラケット添字・範囲構文の体系を拡張。半開区間 `a..<b`、閉区間 `a..=b`、下限除外 `<..` / `<..<`、末尾相対位置 `^k`（`^0` が末尾要素）、多次元添字 `m[i, j]`・`ref t[0..<2, ..]`、スライス刻み幅を導入。`for` の裸 `a..b` を正準形として受理し、終端付き裸 `..` スライスは終端を含む閉区間となる |

### 入力種別ごとのエディション決定規則

| 入力の種類 | 適用されるエディション |
| --- | --- |
| `Tsuzuri.toml` の `[package]` に `edition = "2028"` 等が明記されたパッケージ | 指定されたエディション（依存パッケージも各自の `Tsuzuri.toml` に従う） |
| `Tsuzuri.toml` に `edition` キーがないパッケージ | **`2026`**（将来より新しいエディションが追加されても不変） |
| `Tsuzuri.toml` のないプロジェクト・単一ファイル・`tsuzuri script`・`tsuzuri repl` | 最新の **`2028`**（CLI の `--edition` フラグで `2026` / `2027` / `2028` を明示上書き可能） |
| `tsuzuri fmt` | 対象ディレクトリ（ファイル指定時は親ディレクトリ）直下の `Tsuzuri.toml` の `edition`、存在しなければ最新の **`2028`** |

なお、マニフェストがなく `--edition` も指定していない入力で終端付きの裸 `..` スライス（`ref xs[a..b]`・`ref xs[..b]`）を書くと、Edition 2028 で閉区間に変わったことを知らせる注意警告 `W1013`（`bare_slice_range_meaning_changed`）が出力されます。エディションに依存せず意図が明確になる半開区間 `ref xs[a..<b]` または閉区間 `ref xs[a..=b]` の使用を推奨します。

### エディションの自動移行

既存パッケージを新しいエディションへ引き上げる際は、`tsuzuri fix --edition` を使用します。

```sh
# Edition 2026 から 2027 へ（旧表記の正準化 + 所有引数への own 付与 + _owned 入口への切り替え）
tsuzuri fix --edition 2027 --from 2026 --dry-run app/
tsuzuri fix --edition 2027 --from 2026 app/

# Edition 2027 から 2028 へ（旧版の半開 .. スライスを明示的な ..< へ書き換え、Tsuzuri.toml を更新）
tsuzuri fix --edition 2028 --from 2027 --dry-run app/
tsuzuri fix --edition 2028 --from 2027 app/
```

移行ツールは本体の挙動や公開契約を勝手に変える推測を行わず、移行後のエディションでプロジェクト全体を再型検査してエラーが 0 件であることを確認してからファイルをアトミックに更新します。

## 非推奨化（`@deprecated`）と互換性の例外

### 宣言を非推奨にする手順

1. **タグの付与**: 対象宣言（`def`・`record`・`union`）の `///` ドキュメントコメント内に `/// @deprecated use Module.new_name instead` の行を追加します。`tsuzuri doc` と LSP ホバーに非推奨案内が表示されます。
2. **呼び出し側での警告（`W1005`）**: 別パッケージから参照された際に既定で警告 `W1005` が発生します（同一パッケージ内の参照には警告を出さないため、段階的な内部移行中も自身の `--deny-warnings` ビルドを妨げません）。代替関数が同一シグネチャで明記されていれば `tsuzuri fix --applicability likely` で自動置換できます。
3. **削除とバージョニング**: 標準ライブラリの公開宣言は削除されません。ユーザーパッケージで公開宣言を削除する場合は破壊的変更となるため、`tsuzuri api-diff` で確認のうえ、セマンティックバージョニングに従い互換範囲が変わるバージョン（バージョン 1.0.0 以降は MAJOR、0.x 台では MINOR）を引き上げます。

### 標準ライブラリ拡張に伴う既知の例外

標準ライブラリは削除や破壊的変更を行いませんが、以下の拡張はまれに既存コードへ影響し得るため、実施時にはリリースノートで告知されます。

- **新規標準モジュール名の追加**: 標準モジュール名は予約されるため、同名のユーザーモジュールが存在すると `E1011` となります。
- **標準共用体へのケース追加**: ワイルドカードなしで網羅的 `match` を行っていたコードが `E1021` となるため、原則として破壊的変更と同等の慎重な審査を経た場合のみ行われます。
- **組み込みのモジュール `ObjC` の予約**: Objective-C 連携（[Objective-C 連携](./objective-c.md)）の追加により、`ObjC` は予約モジュール名になりました。同名のユーザーモジュール `ObjC.tz` は `E1011` となります。
- **標準型クラスインスタンスの追加**: オーファン規則により通常の衝突は防がれますが、多相インスタンスや組み込みクラスの拡充によって候補が複数になり曖昧性エラー（`E1043`）が生じる場合があります。

### C ABI の既知の変更

- **`@c_layout` レコードの `extern def` での値渡し**: `ref` のない `@c_layout` レコードを `extern def` の引数・結果に書いたときの C ABI が変わりました。以前は引数を `const T *`、結果を先頭の out 引数で受け渡していましたが、現在は C の構造体の値渡し・値返し（C の `T`）です。ソースはそのままコンパイルでき、診断も出ません。ポインターを取る C の関数をこの形で宣言していたプログラムは、引数を `ref R` に、out 引数を `ref mut R` の引数に書き直してください。`@c_layout` のないレコード、`ref R`・`ref mut R`、`export def`、コールバックは変わりません（[ネイティブ連携と C ABI](./native-interop.md#構造体の値渡しと値返し)）。高速バックエンド（`--backend fast`）は、スカラー 1 つに下がらない値渡しを `E2002` で拒むので、そのプログラムは既定の `--backend llvm` でビルドします。

## `tsuzuri api-diff` による公開 API 互換性検査

パッケージのリリース前には、旧バージョンのワークツリー等と比較して意図しない破壊的変更が混入していないかを `tsuzuri api-diff` で検証します。

```sh
git worktree add ../mylib-prev v0.2.0
tsuzuri api-diff ../mylib-prev . --effective
```

### 変更の判定基準サマリー

| 変更内容 | 判定 | 理由 |
| --- | --- | --- |
| 公開宣言の削除・`private` 化・モジュールや名前空間の改名 | `breaking` | 既存の参照元がリンク・名前解決できなくなるため |
| 関数・定数・型エイリアスのシグネチャ変更、`export` や `const def` の `const` 削除 | `breaking` | 呼び出し側や他モジュールの定数初期化式が破損するため |
| 公開 `record` へのフィールド追加・削除・型変更・順序変更 | `breaking` | 全フィールド指定のリテラル構築式や C ABI 配置が壊れるため |
| 公開 `union` へのケース追加・削除・ペイロード変更・順序変更 | `breaking` | 網羅的 `match` が `E1021` になるため |
| `extern class` の実行時名・基底・`sync` の変更、メンバーの削除やセレクター・型・所有の属性の変更 | `breaking` | 型の関係・スレッドの性質・呼び出しの C の型や所有が変わるため（メンバーの追加は `non-breaking`） |
| 既定実装を持たない `class` メソッドの追加、既存既定実装の削除 | `breaking` | 既存の外部 `instance` 実装がコンパイル不能になるため |
| `deriving` や公開 `instance` の削除、`@requires` の追加、`@ensures` や効果属性（`@no_alloc` 等）の削除 | `breaking` | 満たしていた型クラス制約や事後条件・効果保証が失われるため |
| 新規公開宣言の追加、`export` の追加、既定実装付き `class` メソッドの追加 | `non-breaking` | 既存の呼び出し・実装を壊さない純粋な拡張であるため |
| `///` ドキュメントコメントや `@complexity` / `@since` / `@see` タグの変更、`@deprecated` の追加 | `non-breaking` | 型・ABI 契約は不変であるため |

`--effective` フラグを指定すると、型エイリアス展開後の実効型やエディション補完後の引数渡し規約、ジェネリックテンプレートの純粋性義務まで含めた精密な契約比較が行われます。ただし、`api-diff` は公開宣言の契約を比較するツールであり、関数本体アルゴリズムの実行結果の変化やパフォーマンス特性の変化までは証明しないため、必ず単体テスト（`tsuzuri test`）と併用してください。
